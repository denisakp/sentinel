# ADR 0006 — Encryption envelope v1 (AES-256-GCM, 64 KB chunks, counter-XOR nonce)

- **Status**: Accepted (2026-05-17)
- **Date**: 2026-05-17
- **Deciders**: Denis AKPAGNONITE
- **Tags**: crypto, format, security

## Context

Sentinel offers opt-in encryption of backup artefacts via `encryption_key_env`. The key is a 32-byte secret (AES-256). The implementation streams the backup through a `ChunkEncryptWriter` defined at `internal/crypto/encrypt.go`. Concretely:

- **Cipher**: AES-256-GCM (`crypto/cipher.NewGCM`).
- **Chunk size**: 64 KB (`chunkSize = 64 * 1024`).
- **On-disk framing**: each chunk written as `[4-byte little-endian length][ciphertext + 16-byte GCM tag]`.
- **Base nonce**: 12 random bytes generated once at stream start (`rand.Read`).
- **Per-chunk nonce**: derived by XOR-ing the last 8 bytes of the base nonce with the chunk index (little-endian uint64). The first 4 bytes of the nonce are unchanged.
- **AAD**: the `backup_id` string.
- **Auth tag**: the last 16 bytes of each chunk's ciphertext; the tag of the final chunk is recorded in the manifest's `encryption.auth_tag`.
- **Manifest fields** (`internal/manifest/types.go` `EncryptionInfo`): `algorithm`, `key_derivation`, `iterations`, `salt`, `iv` (= the base nonce), `auth_tag` (= last chunk's tag).

The decrypt path mirrors the encrypt path and is bounded by `chunkSize + gcm.Overhead()` per read to avoid OOM on a malicious length prefix.

This ADR freezes that format as v1 so any future change is a deliberate, ADR-governed event.

## Decision drivers

- Restorability of already-encrypted backups must hold across all future releases of the same major version.
- The nonce scheme must be safe under streaming: AES-GCM forbids nonce reuse under the same key.
- Decrypt must be safe against malicious inputs: a forged length prefix must not allocate gigabytes.
- The format must be expressible in the existing manifest's `EncryptionInfo` fields without schema changes.
- The crypto package becomes a driven adapter under ADR 0001; the port lives in `internal/ports/crypto.go`.

## Options considered

### Option A — Whole-file AES-256-GCM with one nonce

Encrypt the whole backup as a single GCM stream.

**Pros**
- Simplest format.

**Cons**
- GCM is not safe past ~64 GB per nonce.
- Forces buffering the entire file or accepting a non-resumable stream.
- A truncated tail at the end of the file is undetectable until the final byte is read.

### Option B — Chunked AES-256-GCM with random per-chunk nonces

Each chunk has its own 12-byte random nonce, stored inline.

**Pros**
- No counter logic.

**Cons**
- 12 bytes of nonce per 64 KB chunk = ~0.018 % storage overhead. Tolerable, but additive on top of the tag.
- Random nonces can collide with non-negligible probability over very long streams.

### Option C — Chunked AES-256-GCM with counter-XOR nonce derived from a single base nonce

The implementation Sentinel ships today. One random 12-byte base nonce per stream; per-chunk nonce = base XOR chunkIndex.

**Pros**
- Unique nonce per chunk by construction; no collision risk under one key/stream.
- Only the base nonce (12 bytes) is stored, in the manifest, not on the artefact.
- Each chunk is independently authenticated and the framing length prefix bounds decrypt allocations.
- Already implemented and tested (`internal/crypto/encrypt_test.go`).

**Cons**
- The XOR-counter scheme is a custom construction; it is correct (each chunk has a unique nonce under one key) but is not a named standard.
- A bug in the counter (overflow past 2⁶⁴ chunks, i.e. ~10²⁰ bytes) would reuse nonces. The chunk size makes this unreachable in practice but should be asserted.

### Option D — Switch to AES-GCM-SIV

Nonce-misuse-resistant variant.

**Pros**
- Survives accidental nonce reuse.

**Cons**
- Requires a third-party dependency (no stdlib support today).
- Different on-disk shape; breaks existing v1 backups.
- Slower than GCM with no real-world need under this construction.

## Decision

Sentinel freezes the encryption envelope as **v1** with the following on-disk and metadata contract:

- **Cipher**: AES-256-GCM (`crypto/cipher.NewGCM` over `crypto/aes.NewCipher`).
- **Chunk size**: 64 KB plaintext. The final chunk may be shorter.
- **Framing**: stream is a concatenation of `[uint32-le length][ciphertext + 16-byte tag]` records.
- **Nonce**: 12-byte base nonce generated by `crypto/rand` at stream start. Per-chunk nonce = `baseNonce` with its last 8 bytes XOR'd with the chunk index as little-endian uint64.
- **AAD**: the backup's `backup_id`, as ASCII bytes.
- **Manifest `EncryptionInfo`**:
  - `algorithm`: `"AES-256-GCM"`.
  - `key_derivation`: free-form; current values document how the operator's key was sourced (`"env"`, `"derived"`).
  - `iterations`, `salt`: present when `key_derivation` requires them; absent (zero / empty) otherwise.
  - `iv`: hex-encoded 12-byte base nonce.
  - `auth_tag`: hex-encoded 16-byte tag of the final chunk (sanity-check at decrypt time).
- **Decrypt invariants**:
  - Each chunk's length prefix is bounded by `chunkSize + gcm.Overhead()` (= 65 536 + 16). Reads exceeding this fail fast.
  - A truncated stream (incomplete last record) fails authentication.
  - The chunk index is a uint64; the encrypter must error if it would overflow (operationally unreachable, defensively asserted).

The package moves to `internal/adapters/crypto/`. The interface (port) exposed to the domain is at `internal/ports/crypto.go` (`Encrypter`, `Decrypter`). The domain (`internal/domain/backup`, `internal/domain/restore`) never calls AES primitives directly.

## Consequences

### Positive
- The envelope format is now ADR-governed; any change is a deliberate event.
- Streaming encryption with bounded memory both at write and at read.
- Each chunk is independently authenticated; tampering localises to a chunk.
- Storage overhead per chunk = 4 bytes length + 16 bytes GCM tag = 20 B per 64 KB ≈ 0.030 %.

### Negative
- The counter-XOR scheme is custom. Mitigated by tests and by this ADR documenting the construction.
- The chunk size is hard-coded. A future need to support other chunk sizes (e.g. 1 MB for very large databases) requires either a v2 format or a manifest-recorded chunk size.
- Key derivation is described in free-form fields. A future ADR may formalise it.

### Neutral / to watch
- Whether to record the chunk size in the manifest. Today every v1 backup uses 64 KB; recording it now makes a future change purely additive.
- Whether `auth_tag` in the manifest serves any verification purpose beyond a sanity check. The framing already authenticates every chunk.

## Compatibility & migration

- **Restorability**: every encrypted backup produced by v1.1+ matches this v1 envelope and remains restorable indefinitely under this ADR.
- **No format change**: this ADR documents the current implementation; it does not modify it.
- **`sentinel.yaml`**: unchanged (`encryption_key_env` remains the opt-in).
- **CLI**: `sentinel security init-key` is unaffected.

A future ADR introducing a v2 envelope must:

1. Define a way for decrypters to detect v1 vs v2 (e.g. a magic byte at offset 0, or an explicit `envelope_version` field in `EncryptionInfo`).
2. Ship a dual-decoder for at least one major release.
3. Document the deprecation timeline for v1 in `release-notes.md`.

## Enforcement

The chunk-length-prefix invariant is enforced at the read site by `maxChunkSize = chunkSize + 16` and the bound check in `(*ChunkDecryptReader).readChunk` (`internal/crypto/decrypt.go`). Violations return the sentinel `crypto.ErrChunkTooLarge`; auth-tag failures return `crypto.ErrAuthTagFailed`. CLI surfaces map both to the operator-facing message `file corrupt or wrong key` via `internal/cli.FriendlyDecryptError`. See `specs/008-decrypt-oom-cap/`.
